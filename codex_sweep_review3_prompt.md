## What to attack (priority order)

1. **The sitter (RR1b fix).** `SITTER` bash script launched via `Popen(start_new_session=True)` with the API key as argv — argv is visible in `ps` output (is that an acceptable exposure on a single-user laptop? propose better). Does `kill -0 $CPID` correctly detect a *replaced* PID (PID reuse)? The conductor's `finally` terminates the sitter — but if the conductor is SIGKILLed the sitter survives and will stop the box even though the user may immediately restart the sweep; is the 300s grace + re-check sufficient? Does the sitter's curl actually match Vast's stop API shape?
2. **Reconcile/adopt (RR2 fix).** `reconcile()` adopts any remote result with `status=success` and matching `trial_id` — but attempt_uuid is NOT checked against anything on adopt. Can a success from a DIFFERENT plan/code era (same trial id impossible? trial id includes code_rev+data_digest — but the remote path is only `/root/sweep/<tid>/`) be adopted? What if two sweeps share the box sequentially — do stale `/root/sweep` trees need a manifest-scoped namespace? Also: adopt path writes `attempts: attempts` (not incremented) — any counter drift?
3. **The in-group wall timer.** `( sleep N; kill -- -$PGID )&` — the timer subshell is itself in the group it kills: does the kill terminate the timer before it completes the group kill (self-kill ordering)? `trap finish EXIT` kills WALL and HB — after a *successful* run the timer dies, fine; after `fail()`'s `exit 1`, does the trap fire before the result write is visible (ordering of result vs group death)? Verify against bash semantics, not intuition.
4. **Money math (RR3 fix).** `billed = start_credit - live_credit` — Vast bills storage/other instances on the same account: other-instance charges inflate "billed" and can falsely trip the sweep cap (conservative, but is it acceptable?). `guard_money` runs before each attempt but not during a 3-hour trial — per-attempt deadline bounds that; verify `deadline = per_trial_cap / dph * 3600` arithmetic and its interaction with `poll_attempt`'s `deadline_s + 2*POLL_S` grace.
5. **Baseline gate (RR14 fix).** The baseline runs once per run_dir; if lm-eval/vLLM versions change on the box later (retry waves days apart), floors drift silently — should the baseline env_digest be required to match trial env_digests? BASELINE_SCRIPT skips the disk/clean-repo checks the trial script has — justified for eval-only? The baseline uses the same `attempt_cap` semantics — what happens when baseline fails twice (sweep aborts — correct?)?
6. **Smoke suite executability.** Walk each scenario line by line as if running it: S1's `N_UUIDS` counting via `ls | head -1 | xargs ls | wc -l` — does it count what it claims? S4's "accelerate never launched" grep chain — correct polarity? S5 reuses `/root/sweep` wipe — does that interact with S1's leftover state? Would the suite as written actually go green on a correct implementation (false-failure risk), and red on each seeded defect (false-pass risk)? Rewrite anything broken.
7. **`04` prefix-diff labels.** Append-stability check compares `len(template(msgs[:i+1]))` monotonically — chat templates often add a generation prompt or strip earlier think-blocks; does the check catch Qwen3.5's actual template behavior (inspect it), and does tokenize=True return lists (not BatchEncoding) across transformers 5.16?
8. **Anything else the rewrite introduced** — races, quoting in the doubled-brace `.format()` templates (three heredoc layers now), `run_attempt`'s `extra` dict merge (`| (extra or {})`) shadowing config keys, HALT semantics when it appears between reconcile and launch.
